# V2 공통 알림함 연결

## 이번 범위

- 일정 등록: 기존 전체 가족 알림 유지.
- 이름·메모 변경: 기존 담당자에게 변경 안내.
- 날짜·시간 변경: 기존 담당자에게 재수락 요청.
- 재수락 거절: 전체 현재 가족에게 재모집 안내.
- 수락·재수락 완료: 현재 주보호자에게 결과 안내.
- 재수락 거절: 주보호자는 거절 안내, 일반 가족은 재모집 안내로 구분.
- 일정 삭제: 현재 가족에게 삭제 안내와 읽음 처리 제공. 일반 일정 상세는 열지 않는다.
- 담당자 교체는 기획에서 제외한다. 자동 만료·긴급 미확인·72시간 재알림과 푸시의 현재 연결 상태는 아래 후속 절을 따른다.

## 연결 구조

Flutter 알림함은 `GET /schedules/schedule-notifications?scope=v2`를 사용한다.
알림 ID와 `next_before_id`는 문자열로 보존한다. 기존 숫자 ID도 문자열로 읽는다.
기본 `scope=all` API와 팀원 일정 처리 코드는 유지한다.

목록과 `/activity/badges`의 알림 개수는 같은 `visible_v2` 함수를 사용한다.
같은 일정의 변경 알림도 각 문서의 읽음 상태를 따로 계산한다.
자동 만료 재모집도 표시하며, `reason=response_timeout`과 원래 수신자 목록을 유지해 재수락 거절 안내와 구분한다.
필터로 빈 페이지가 나와도 반환된 커서로 다음 페이지를 조회할 수 있다.

알림 선택 시 서버에서 현재 권한·일정 정보를 재검사하고 읽음 처리한다.
현재 참여 공간 목록을 새로 확인한 뒤, 다른 공간이면 확인창 없이 해당 공간을 자동 선택한다. 참여 종료·삭제 공간에는 진입하지 않는다.
해당 일정의 월별 API 응답으로 `Schedule`을 구성해 기존 `ScheduleDetail`을 연다.
상세의 재수락·거절·수락 권한과 응답은 기존 일정 구현을 사용한다.
과거 요청 알림을 열어도 상세는 최신 일정과 최신 요청을 기준으로 표시한다.
알림 확인만으로 재수락이나 거절을 자동 실행하지 않는다.

## 확인 순서

1. 담당자가 있는 일정의 이름·메모를 변경하고 담당자 알림과 배지를 확인한다.
2. 날짜·시간을 변경하고 담당자가 알림에서 상세로 들어가 전후 내용·재수락·거절을 확인한다.
3. 재수락하면 기존 일정 배정이 유지되는지 확인한다.
4. 별도 일정에서 거절하고 전체 현재 가족의 재모집 알림과 수락 가능 상태를 확인한다.
5. 다른 공간 알림의 자동 전환과 참여 종료 계정의 접근 차단을 확인한다.
6. 목록 읽음 표시와 Drawer 숫자가 함께 갱신되는지 확인한다.

서버를 재시작하고 앱을 Hot Restart한다. Firestore 색인은 팀원의
`firestore.indexes.json`이 Firebase 프로젝트에도 반영되어 있어야 한다.
기존 담당자가 없는 일정의 변경 알림 발행 및 pending 자동 재시도는
팀원 문서 `schedule_notifications.md`의 미연결 항목으로 남긴다.
이번 작업은 MySQL 테이블을 변경하지 않는다.

삭제 전 알림은 기존 서버 정책대로 숨기고 삭제 알림으로 안내한다. 수락·재수락 결과 알림은 새로 처리한 요청부터 생성되며 과거 결과를 소급 발행하지 않는다. 준비 실패는 DB 작업을 rollback하고, commit 후 발행 실패는 수락 결과를 유지한다. 수락 결과 pending의 자동 재발행은 이번에 추가하지 않았다.

기존 V2 필터가 제외하던 만료·미응답·자동 재모집·긴급 미확인을 앱 알림함·배지·FCM에 연결했다. B의 기한 계산·배정 해제·알림 생성 조건은 변경하지 않았다. 상세 수신자와 검수 기준은 아래 표 및 [일정 알림 전체 연동 안내](schedule_notifications.md)를 따른다.


## 후속 — 일정 참여 취소 주보호자 알림

B의 참여 취소 처리·재모집 앱 표시는 사용자 확인 완료. 주보호자용 schedule_withdrawn은 V2 알림함·배지·전용 제목·푸시 연결이 남아 있다. reason=participation_withdrawal인 재모집을 재수락 거절로 오표시하지 않도록 한다. [참여 취소 인수인계](schedule_withdrawal.md)와 [다음 업로드 전달 기록](schedule_handoff_2026-10-29.md)을 참고한다.


## 개인 알림 삭제

- `DELETE /schedules/schedule-notifications/{notification_id}`: 현재 접근 가능한 알림 한 건을 본인 목록에서 숨긴다.
- `DELETE /schedules/schedule-notifications`: 앱 알림함(`scope=v2`)에 해당하는 모든 페이지의 접근 가능한 알림을 본인 목록에서 숨긴다. 새로 생성되는 미래 알림은 삭제하지 않는다.
- 기존 Firestore `schedule_notifications/{notification_id}/reads/{sha256(user_id)}` 문서에 `deleted_at` 서버 시각을 병합 저장한다. 기존 `read_at`, 공용 원본, 상대 가족의 문서와 MySQL 일정은 유지한다.
- 목록·상세·개별 읽음·배지가 같은 개인 삭제 상태를 확인한다. 삭제한 항목은 배지에서 제외되고 다음 페이지 커서는 유지한다. 읽음 조회와 삭제 상태 확인을 한 번의 문서 읽기로 수행한다.
- 삭제 전 확인하며, 처리 중 중복 클릭을 막는다. 성공 응답 후 목록을 갱신하고 배지를 다시 조회한다. 계정 전환·이전 페이지의 늦은 응답이 삭제 결과를 덮어쓰지 않는다.
- 전체 삭제는 권한 검사 후 400건 이하 배치로 저장한다. 여러 배치 전체가 하나의 트랜잭션은 아니므로 중간 장애에서는 일부만 반영될 수 있다. 재조회 후 다시 삭제할 수 있으며, 이미 삭제된 문서는 목록에서 제외된다.
- 초대 삭제·전체 읽음 기능은 포함하지 않는다. MySQL 테이블·컬럼 추가와 별도 Firebase 콘솔 설정은 필요 없다.
- 서버를 재시작하고 앱을 다시 실행해 확인한다. 두 가족 계정으로 본인의 삭제가 상대방의 목록·일정에 영향을 주지 않는지 검증한다.


## 참여 철회 알림 연결

`docs/schedule_withdrawal.md` 마지막 절의 A 후속 연결을 적용했다. `schedule_withdrawn`의 앱 제목·아이콘·FCM, 철회 후 재모집의 문구 구분, 작업자 제외를 연결한다. 목록·배지·삭제·읽음은 기존 개인별 알림 처리를 그대로 사용한다. 담당자 교체는 구현하지 않기로 확정되어 이번 범위에서 제외한다. 실제 기기 검수는 서버와 앱 재시작 후 별도로 수행한다.


## 자동 처리 알림 수신·표시·푸시

| 유형 | 수신자 | 제목/푸시 안내 |
|---|---|---|
| `schedule_reconfirm_expired` | 현재 가족인 기존 담당자 | 재수락 기한 만료와 담당 배정 해제 |
| `schedule_reconfirm_unanswered` | 현재 주보호자 | 담당 가족의 미응답과 배정 해제 |
| `schedule_recruitment` (`reason=response_timeout`) | 현재 전체 참여 가족 | 담당자 재모집, 주보호자에게도 거절로 변환하지 않음 |
| `schedule_reconfirm_unverified` | 현재 주보호자 | 긴급 재수락 미확인, 담당 가족에게 직접 확인 |

- 자동 이벤트이므로 작업자 제외를 새로 적용하지 않는다. 생성 시 확정한 `recipient_ids`를 확대·재작성하지 않고 현재 공간 참여·계정·일정 식별 검사를 유지한다.
- V2 목록과 배지는 동일한 허용·권한·개인 삭제 기준을 사용한다. 기존 읽음/삭제 상태와 문자열 이벤트 ID를 보존한다.
- 기존 발행 함수가 새 이벤트를 `pending`에서 `published`로 바꿀 때 FCM 대기 상태를 함께 기록한다. 이미 `published`인 과거 이벤트는 앱에서 표시될 수 있지만 기기 푸시는 소급 발송하지 않는다.
- 제목과 아이콘을 유형별로 구분한다. 푸시를 누르면 본인 계정을 확인하고 알림함을 열며, 항목을 누르면 참여 권한을 확인해 해당 공간의 최신 상세를 연다. 과거 만료 알림을 열어도 일정이 다시 배정되거나 과거 상태로 복원되지는 않는다.
- 긴급 미확인은 확인 안내이며 이번 연결로 자동 수락·거절·배정 해제를 추가하지 않는다. 기존 기한 계산과 시작 시각 기준을 유지한다.
- API와 **통합 알림 worker**를 각각 재시작하고 앱을 Hot Restart한다. `python -m python.features.schedules.reminder_worker` 하나로 검사·재시도·푸시를 실행한다. 별도 재수락 worker를 중복 실행하지 않는다.
- MySQL·패키지·Firestore 색인 추가 변경은 없다. 정상 이벤트 발행과 별개인 다른 유형의 pending 자동 복구 확대는 이번 범위가 아니다.

### 실제 기기 검수 순서

1. 다른 가족에게 배정된 일정의 날짜/시간을 변경하고 재수락 요청의 응답 기한을 확인한다.
2. 응답하지 않은 채 기한을 넘긴 후 기존 담당자는 만료 안내, 주보호자는 미응답 안내, 현재 가족은 재모집을 확인한다. 주보호자에게 재모집이 거절로 표시되지 않는지 확인한다.
3. 기한이 없는 긴급 요청은 기존 서버 조건에 따라 시작 시각까지 미확인일 때 주보호자에게 별도 확인 안내가 오고, 해당 안내만으로 배정이 해제되지 않는지 확인한다.
4. 각 기기에서 푸시 도착 → 본인 알림함 → 상세 이동을 확인한다. 개인 읽음/삭제와 배지가 맞는지 확인한다. 종료된 참여자·다른 공간 계정에게는 공개되지 않아야 한다.

자동 테스트는 DB·Firestore·FCM을 대체한다. 실제 공유 DB의 시간을 바꾸거나 과거 알림을 재발송하지 않았다. 실제 기기 수신은 위 순서로 별도 검수한다.
