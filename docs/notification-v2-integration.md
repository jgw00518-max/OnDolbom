# V2 공통 알림함 연결

## 이번 범위

- 일정 등록: 기존 전체 가족 알림 유지.
- 이름·메모 변경: 기존 담당자에게 변경 안내.
- 날짜·시간 변경: 기존 담당자에게 재수락 요청.
- 재수락 거절: 전체 현재 가족에게 재모집 안내.
- 수락·재수락 완료: 현재 주보호자에게 결과 안내.
- 재수락 거절: 주보호자는 거절 안내, 일반 가족은 재모집 안내로 구분.
- 일정 삭제: 현재 가족에게 삭제 안내와 읽음 처리 제공. 일반 일정 상세는 열지 않는다.
- 교체·자동 만료 안내·72시간 재알림·푸시는 이번 연결 범위에서 제외한다.

## 연결 구조

Flutter 알림함은 `GET /schedules/schedule-notifications?scope=v2`를 사용한다.
알림 ID와 `next_before_id`는 문자열로 보존한다. 기존 숫자 ID도 문자열로 읽는다.
기본 `scope=all` API와 팀원 일정 처리 코드는 유지한다.

목록과 `/activity/badges`의 알림 개수는 같은 `visible_v2` 함수를 사용한다.
같은 일정의 변경 알림도 각 문서의 읽음 상태를 따로 계산한다.
자동 만료 재모집은 `request_history_seq`가 있는 문서로 구분해 제외한다.
필터로 빈 페이지가 나와도 반환된 커서로 다음 페이지를 조회할 수 있다.

알림 선택 시 서버에서 현재 권한·일정 정보를 재검사하고 읽음 처리한다.
현재 참여 공간 목록을 새로 확인한 뒤, 다른 공간이면 이동 여부를 묻는다.
해당 일정의 월별 API 응답으로 `Schedule`을 구성해 기존 `ScheduleDetail`을 연다.
상세의 재수락·거절·수락 권한과 응답은 기존 일정 구현을 사용한다.
과거 요청 알림을 열어도 상세는 최신 일정과 최신 요청을 기준으로 표시한다.
알림 확인만으로 재수락이나 거절을 자동 실행하지 않는다.

## 확인 순서

1. 담당자가 있는 일정의 이름·메모를 변경하고 담당자 알림과 배지를 확인한다.
2. 날짜·시간을 변경하고 담당자가 알림에서 상세로 들어가 전후 내용·재수락·거절을 확인한다.
3. 재수락하면 기존 일정 배정이 유지되는지 확인한다.
4. 별도 일정에서 거절하고 전체 현재 가족의 재모집 알림과 수락 가능 상태를 확인한다.
5. 다른 공간 알림의 이동 확인·취소와 참여 종료 계정의 접근 차단을 확인한다.
6. 목록 읽음 표시와 Drawer 숫자가 함께 갱신되는지 확인한다.

서버를 재시작하고 앱을 Hot Restart한다. Firestore 색인은 팀원의
`firestore.indexes.json`이 Firebase 프로젝트에도 반영되어 있어야 한다.
기존 담당자가 없는 일정의 변경 알림 발행 및 pending 자동 재시도는
팀원 문서 `schedule_notifications.md`의 미연결 항목으로 남긴다.
이번 작업은 MySQL 테이블을 변경하지 않는다.

삭제 전 알림은 기존 서버 정책대로 숨기고 삭제 알림으로 안내한다. 수락·재수락 결과 알림은 새로 처리한 요청부터 생성되며 과거 결과를 소급 발행하지 않는다. 준비 실패는 DB 작업을 rollback하고, commit 후 발행 실패는 수락 결과를 유지한다. 수락 결과 pending의 자동 재발행은 이번에 추가하지 않았다.

기존 V2 범위에서 제외했던 자동 만료 안내·자동 만료 재모집은 아직 앱 표시 연결이 필요하다. B의 자동 배정 해제는 검수됐고, B는 기한 있는 긴급 요청의 만료 알림 발행 조건을 수정했다. A의 V2 필터·제목·배지·푸시 후속 사항과 수신자/검증 기준은 [일정 알림 전체 연동 안내 9절](schedule_notifications.md#9-2026-10-29-자동-만료-알림-ab-인수인계)을 따른다. 이 문서 추가만으로 연결 완료를 의미하지 않는다.
