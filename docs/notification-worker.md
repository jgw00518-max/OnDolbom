# 통합 알림 worker 실행

프로젝트 루트에서 알림 담당자 한 명만 다음 명령을 실행한다.

```powershell
python -m python.features.schedules.reminder_worker
```

API는 별도 터미널에서 기존처럼 실행한다. 기본 API 실행은 worker를 시작하지 않는다.

```powershell
python -m uvicorn python.main:app --host 0.0.0.0 --port 8000 --reload --no-access-log
```

## 한 명령으로 실행하는 작업

| 작업 | 주기 |
|---|---|
| 72시간 재알림 대상 검사 | 검사 완료 후 60초 |
| 일정 FCM 푸시 대기열 | 작업이 있으면 5초, 비면 10→15초, 오류 시 15초 |
| 채팅 MySQL 푸시 대기열 | 검사 완료 후 5초 |
| 재수락 기한 만료·긴급 미확인 검사 | 60초, 처리 시간을 제외하고 대기 |
| 기존 미발행 알림 재시도 | 60초, 처리 시간을 제외하고 대기 |

업무 함수와 저장 계약은 기존 기능별 파일에 유지한다. 통합 프로그램은 한 Python 프로세스 안에서 작업별 스레드를 시작한다. 각 함수가 자체 DB 연결을 사용하며 연결을 공유하지 않는다. 같은 작업을 중복 실행하지 않고, 느린 요청·예외가 다른 작업의 주기를 막지 않게 한다. 작업 실패는 기록하고 다음 주기에 재시도한다.

## 종료와 기존 실행 전환

1. 실행 중인 기존 worker 터미널에서 Ctrl+C로 종료한다.
2. 별도로 실행한 `python.features.schedules.reconfirm_expiry_worker`도 종료한다.
3. 위 통합 명령을 한 번만 실행한다. 이제 별도 재수락 worker는 켜지 않는다.
4. 종료는 통합 worker 터미널에서 Ctrl+C를 누른다. 대기 작업은 즉시 깨우며 실행 중 I/O에는 최대 5초의 공통 종료 시간을 준다. 작업별 자식 프로세스는 생성하지 않는다.

다른 팀원은 API만 실행한다. worker는 같은 MySQL·Firebase 프로젝트를 대상으로 동작해야 한다. 서로 다른 로컬 DB를 쓰면 각 DB의 작업은 공유되지 않는다.

`ONDOLBOM_REMINDER_WORKER=1`을 명시해 API와 함께 실행하는 기존 선택 기능도 같은 통합 명령을 호출한다. 별도 터미널의 worker와 동시에 사용하지 않는다. 기본값 0과 API/worker 분리 정책은 유지한다.

## 한 번 검사

```powershell
python -m python.features.schedules.reminder_worker --once
```

모든 작업을 병렬로 한 번 검사하고 종료한다. 실제 환경에서 실행하면 DB 배정 해제·알림 저장·FCM 발송까지 수행할 수 있는 운영 명령이다. 자동 테스트는 관련 함수를 대체해 외부 DB·Firebase를 호출하지 않는다.

## 범위

실행 통합은 기존 작업을 함께 실행하도록 바꾸는 것이다. 통합 자체가 목록/제목/FCM 연결이나 재시도 대상 유형을 변경하지는 않는다. 별도 후속 작업으로 재수락 자동 만료·미확인의 앱/FCM 연결은 완료했다. 해당 연결 상태는 `schedule_notifications.md`와 `notification-v2-integration.md`를 참고한다. DB·패키지 변경은 없다.


### DB 확정 후 미발행 알림 복구

통합 worker는 1분마다 pending 알림을 확인합니다. 등록·변경·재수락 요청·수락·재수락 결과도 기존 만료·삭제·철회 알림과 함께 재시도합니다. 등록은 일정 생성 시각, 변경과 요청은 해당 이력, 수락 결과는 현재 담당자·수락 시각 및 재수락 응답 이력을 검증합니다. 롤백되거나 이후 상태가 변경되어 유효하지 않은 결과는 발행하지 않습니다.

공간 삭제(`family_room_deleted`)도 같은 pending 조회와 푸시 큐를 재사용합니다. DB에 확정된 공간 생성 시각·삭제 시각을 검증한 뒤 발행하며 최초 수신자·읽음 상태를 유지합니다. 별도 worker나 조회 주기를 추가하지 않습니다.

공통 publish의 pending → published 전환을 사용하므로 이미 발행된 문서는 읽음 기록을 초기화하거나 푸시를 다시 예약하지 않습니다. worker가 꺼져 있으면 자동 복구하지 않으며, 과거 누락 중 pending 문서가 남아 있는 경우에만 복구할 수 있습니다. DB 스키마 변경은 없습니다.
